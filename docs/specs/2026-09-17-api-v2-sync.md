# API v2 sync — call reviews, call recording, webhook events

Status: Implementation plan · 2026-09-17 · targets the release after v0.2.0

## Why

`docs/modjo-openapi.full.json` was bundled at v0.2.0 (2026-06-25) from the live
spec at <https://api.modjo.ai/v2/open-api.json>. Re-fetching it today shows the
API has moved on. Diffing the two specs (operations, schemas, tags) yields
exactly three changes — no removals, no changed operations:

| # | Change | Kind |
|---|---|---|
| 1 | `GET /call-reviews` + tag `Call Reviews`, schemas `CallReview`, `CallReviewAnswer`, `CallReviewAnswerQuestion`, `CallReviewTemplate`, `CallReviewListResponse` | New endpoint |
| 2 | `GET /calls/{id}/recording` + schema `CallRecording` | New endpoint |
| 3 | `Webhook.events` enum grew from 3 to 7 values (`call_created`, `call_tag_added`, `call_tag_removed`, `call_transcribed` added), in `Webhook`, `CreateWebhookRequest` and `UpdateWebhookRequest` | Widened enum |

Nothing is breaking: existing CLI surface stays valid. This is additive parity
work plus a docs refresh.

## Non-goals

- No MCP changes. `internal/mcp` proxies whatever tools the upstream MCP server
  advertises; it does not enumerate REST endpoints.
- No client-side validation of webhook event names. The spec models `events`
  items as `anyOf[enum, string]`, i.e. the server deliberately accepts names it
  has not published yet. Validating locally would break the CLI every time
  Modjo ships an event before we ship a release.

## Design

Every piece follows the recipe in `ARCHITECTURE.md` ("Adding a resource
command"): model + filter + client method in `internal/api`, a thin
`internal/cmd/<group>` package rendering `output.Field`s, registration in
`internal/cmd/root`, and a `.txtar` script for the user-facing contract.

### 1. `modjo call-reviews list` (`GET /call-reviews`)

Top-level group, not a `calls` sub-command: the endpoint is workspace-scoped and
takes no call id, so it mirrors `crm-templates` rather than `calls tags`.
`GroupID: "core"` — it is read-only conversation data like calls and deals.

**Models** (`internal/api/models.go`):

```go
type CallReview struct {
    ID, CallID, RevieweeID, CreatedByID json.Number
    Template                            CallReviewRef
    Rating                              json.Number   // 0-4 weighted avg; null -> ""
    IsPrivate, IsAiGenerated            bool
    CreatedOn, ModifiedOn               string
    Answers                             []CallReviewAnswer
}
type CallReviewAnswer struct { ID, Weight, Rating json.Number; Question CallReviewRef; Feedback string }
type CallReviewRef   struct { ID json.Number; Title string }  // template + question share this shape
```

`json.Number` (not `float64`) for `rating` and the nullable ids: decoding JSON
`null` into a `json.Number` leaves it `""`, which is how the rest of the package
already distinguishes "absent" from `0`. That matters here — `rating` is null
when the reviewer marked every question N/A, and a per-answer rating of `-1`
means not-applicable, so a silent `0` would read as "scored zero".

`CallReviewAnswerQuestion` and `CallReviewTemplate` are structurally identical
`{id, title}` objects, so one `CallReviewRef` type serves both — the same call
`TeamMember = User` makes.

**Filter** (`internal/api/filters.go`): `CallReviewFilter{Since, Until, Order, Limit}`
→ `startDateTime`, `endDateTime`, `order`. Note these are camelCase, unlike the
snake_case params everywhere else in v2; the filter is the only place that
knows, exactly as intended.

**Client**: `CallReviews(ctx, f) iter.Seq2[CallReview, error]` over `paginate`.

**Command**: `call-reviews list` with `--since`/`--until` (through
`cmdutil.NormalizeDateFlag`, so `7d` works like it does on `calls list`) and
`--order asc|desc`, validated as a usage error. Table columns:
`ID, CALL, TEMPLATE, REVIEWEE, RATING, AI, CREATED`. Nested `answers` stay out
of the table and are reached via `--json`, the same way expanded call relations
already are.

### 2. `modjo calls recording <callId>` (`GET /calls/{id}/recording`)

A plain object response (no `{data}` envelope), so a direct `doJSON` get:
`GetCallRecording(ctx, id) (CallRecording, error)` returning
`{url, expiresAt, mediaType}`.

Sits in the existing `calls` group next to `transcript`/`summary`. Columns:
`URL, EXPIRES, TYPE`. An `--open` flag opens the signed URL via the existing
`cmdutil.OpenResource` helper (`accounts open` already does this), which is the
main thing a human wants from a 1-hour signed link.

The endpoint has a distinctive `410 Gone` ("recording deleted for data
retention"). `ExitCodeForError` currently maps 410 to the generic `ExitError`
(1). Map it to `ExitNotFound` (5) instead: for a scripting caller, "the
recording is not there" is the same branch whether it was deleted or never
existed, and 5 is already documented as the not-found code. The upstream
message still explains which of the two it was.

### 3. Webhook events

Flag help on `webhooks create --event` and `webhooks update --event` lists all
seven values; the `Webhook.Events` comment in `models.go` follows. No code path
changes — see non-goals.

## Test plan

The repo gates on 95% statement coverage (`make cover`), so each layer gets
tests in the style already there:

- `internal/api/parity_test.go` — one `recordingServer` case per new client
  method, asserting method, path, query and decoded values; plus a decode case
  proving `rating: null` stays empty and `-1` survives.
- `internal/cmd/callreviews/*_test.go` and a `calls recording` case in
  `internal/cmd/calls` — httptest-backed command tests.
- `test/script/call_reviews.txtar` and a `calls recording` block in
  `test/script/calls_subresources.txtar`, with the stub server in
  `cmd/modjo/script_test.go` gaining `/v2/call-reviews` and
  `/v2/calls/{id}/recording` routes.
- `internal/cmdutil/exit_test.go` — 410 → 5.
